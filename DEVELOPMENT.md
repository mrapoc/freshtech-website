## Checks from the repository root

```
npm run lint
npm run test
npm run build:no-prerender
```

Use the full npm run build when routing, prerendering or deployment output changes.
It generates sitemap/RSS files and prerenders routes, so review generated diffs and
inspect current lifecycle scripts before running. A fast build is not proof that
prerendering passed. Do not repeat builds merely because an agent turn ends.

## Generated page performance checks

Layout navigation labels come from `data/navigation.ts`, which derives slug and
h1 from `data/content.ts` at runtime. Production builds replace that module with
a literal projection generated by `scripts/content-chunks.mjs`, so the eager
bundle excludes the full industry and problem records. Do not hand-edit labels;
`scripts/navigation-links.test.ts` asserts the two projections match.

The full build runs `npm run check:page-budgets` after prerendering. This checks
every generated page for a main heading, canonical, its CSS delivery contract, valid
initial module assets and byte budgets. It also checks sitemap output coverage.
Run it separately only against a freshly completed full build, not old `dist` files.

Limits are 400 KB HTML, 55 KB gzipped HTML, 200 KiB inline CSS and 400 KB gzipped
initial modules per page, with a tighter 210 KB homepage module limit. Module
measurement covers the emitted module scripts and preload hints, not later user
interactions. These are regression limits, not a promise of a Google score.

The homepage instead has a 30 KB gzipped HTML limit and 32 KB critical CSS limit.
Beasties 0.5.4 extracts CSS from the final SSR document; only its CSS output is
used, preserving the original React HTML. All original font faces are retained.
The full hashed stylesheet loads asynchronously with a no-JavaScript fallback.
Other routes retain complete inline CSS. Node 20.19 or newer is required.
Built browser checks cover font loading, blocked full CSS and layout stability
when the complete stylesheet arrives at five viewport widths.

Keep `data/content.ts` as independent exported literal records. The build splits
those records into separate modules so each route loads its relevant content.
Executable expressions, imports and cross-record references fail the build.
Review bundle growth before increasing a limit. After a material performance
change, compare like-for-like mobile runs on the worker and verify production
with Google PageSpeed. Record all four categories and the run URL.

## Browser journey checks

Start npm run dev for interactive checks. Exercise changed navigation and forms
at phone and desktop sizes, inspect screenshots, keyboard access and browser errors.
Use npm run test:e2e for Playwright tests. The test server uses port 5188; the
fixture blocks external services and non-GET requests. E2E_BASE_URL can select
another local server. Normal development remains on port 5173. Tests use real
pathname routes, route-specific canonicals and mocked booking recovery.

Prerender, hydration, bundled CSS and published article checks require production HTML. Run
`npm run test:e2e:built`; it performs a fresh full build, starts Vite preview on
port 5189 and runs the dedicated Chromium suite. When `E2E_BASE_URL` names an
already served fresh worker build, the suite uses that URL instead of starting
its own preview. Skipped checks are not passes.

The homepage uses true React SSR and hydration; other routes retain browser
prerendering. `build:ssr-home` emits a build-only entry into ignored `dist-ssr`.
Prerender finalises the homepage after all route captures. Page checks require
one valid homepage hydration snapshot and reject its presence on other routes.
Keep the first server/client tree identical. Responsive hero and navigation
geometry belongs in CSS; dates use the serialised snapshot and UK time zone.

An isolated worker can opt into an explicitly installed Chromium-compatible
browser by setting `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` to its executable path.
When set, prerendering and the E2E `chromium` project launch that executable with
Chromium sandboxing enabled. Other E2E browser projects and runs without the
variable keep Playwright's normal browser selection and launch defaults. For example:

macOS/Linux:

```sh
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/path/to/chrome npm run build
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/path/to/chrome npm run test:e2e -- --project=chromium
```

Windows PowerShell:

```powershell
$env:PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH = 'C:\path\to\chrome.exe'
npm run build
npm run test:e2e -- --project=chromium
```

Only use a browser executable supplied by the controlled worker environment.
Playwright warns that custom browser executables can be incompatible with its
bundled browser protocol, so this remains an explicit worker-only override.

## Native Astro checks

The live native site lives in `prototypes/html-first-slice`. Node 24 is used for CI. Run from the
subproject directory with `ASTRO_TELEMETRY_DISABLED=1` set (`export ASTRO_TELEMETRY_DISABLED=1`
on macOS/Linux, `$env:ASTRO_TELEMETRY_DISABLED = '1'` in PowerShell):

```
npm ci
npm test
npm run test:consent
npm run test:pricing
npm run test:homepage-enhance
npm run test:contact
npm run test:guides-enhance
npm run test:problems
php -n server/tests/website-proof-test.php
php -n server/tests/google-rating-test.php
npm run test:proof
npm run build
```

The native build must validate every emitted HTML route using the shared
quality contract as well as family-specific content/metadata checks. See
[the static quality contract](docs/seo/static-quality-contract.md). New pages
must be discovered automatically, and a violation must fail the build.

For browser checks, use the verified Playwright module and an explicit full
Chromium/Edge executable. Every launch must keep `chromiumSandbox: true`.
The root lockfile provides Playwright for CI; worker paths come from its private
profile. Do not copy that profile, credentials or customer source records.

```
node scripts/quality-browser-check.mjs
npm run verify:homepage-browser
npm run verify:browser
npm run verify:pricing-browser
npm run verify:proof-browser
npm run verify:case-studies-browser
npm run verify:locations-browser
npm run verify:industries-browser
npm run verify:blog-browser
npm run verify:service-locations-browser
npm run verify:technology-browser
npm run verify:guides-browser
npm run verify:consent-ui
npm run verify:fonts
```

The route sweep covers all built pages. Focused checks retain meaningful
interactions and font/layout regressions that a generic sweep cannot prove.
Provider requests are mocked, and the normal contact output remains disabled.
Problem-family browser checks require a separately staged synthetic output via
`scripts/stage-problem-fixture.mjs` and `PROBLEM_TEST_DIST`; then run
`npm run verify:problems-browser`. Never use canonical customer records in the
worker packet. The default build rejects fixture mode and compares canonical
testimonial values locally.
Do not package a form-test build. `node scripts/quality-gate.mjs` runs these
checks locally (the Mac deploy runs it before every release); the `Static site
quality` workflow runs the same steps on GitHub, by hand only. Their success is
build/browser evidence, not proof of a production rollout or a Google score.

`verify:proof-browser` reads `dist-production` by default; set `PROOF_DIST=dist`
to check preview output. It mocks only anonymous public feeds with synthetic data
and never adds fixtures to the build. The PHP tests read synthetic snapshot
files under `php -n`; they are not live Apache evidence.
For production, set `PUBLIC_SITE_MODE=production` and run `npm run build`, then
follow the public proof release checks (kept privately in `~/Context/FreshTech/Website/internal-docs/`). Updating
the existing site uses `node scripts/package-static-production.mjs
--preserve-existing-endpoints` from the repository root.
